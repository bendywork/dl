# 企业级爬虫架构设计

## 📌 核心问题
> 如何设计一个可扩展、可维护、能应对反爬的企业级爬虫系统？三层架构如何划分职责？

## 🌱 根源与动机

### 爬虫项目的天然复杂性
爬虫项目看似简单（发请求 → 解析页面 → 存数据），但在企业场景下会面临：

1. **数据源多样化** — 同时爬 API、HTML 页面、PDF 文件
2. **反爬对抗** — 每个站点的反爬策略不同，需要灵活切换策略
3. **数据量爆炸** — 股票市场有 5000+ 只股票，每只每天产生大量数据
4. **容错需求** — 网络抖动、IP 被封、验证码拦截，必须有断点续传

### 为什么传统的"一个脚本跑到底"不行？

```
❌ 错误方式：一个 main.py 搞定一切
main.py:
  → requests.get(url) 
  → BeautifulSoup 解析
  → pymysql 直接插库
  
问题：改数据源要改请求逻辑，改反爬要改解析逻辑，牵一发动全身
```

## 📐 三层架构设计

本项目采用的是 **调度层 → 解析层 → 存储层** 三层架构：

```
┌─────────────────────────────────────────────────┐
│                  调度层                           │
│  ┌─────────────┐  ┌──────────────┐              │
│  │ HTTP 引擎    │  │ 浏览器引擎    │              │
│  │ (httpx)     │  │ (Playwright) │              │
│  └──────┬──────┘  └──────┬───────┘              │
│         ↓                ↓                      │
│  ┌──────────────────────────────────┐           │
│  │       解析层 (parsel/selectolax)  │           │
│  └──────────────┬───────────────────┘           │
│                 ↓                               │
│  ┌──────────────────────────────────┐           │
│  │      存储层 (Peewee + DBUtils)    │           │
│  └──────────────────────────────────┘           │
└─────────────────────────────────────────────────┘
```

### 各层职责

| 层级 | 职责 | 核心组件 | 不允许做的事 |
|------|------|---------|-------------|
| **调度层** | 请求调度、并发控制、去重、反爬 | Crawlee、httpx、Playwright | 不解析数据、不存数据库 |
| **解析层** | HTML/CSS/XPath 选择器、字段提取 | parsel、selectolax、BeautifulSoup | 不发起请求、不关心数据从哪来 |
| **存储层** | 数据库连接池、批量写入、去重 | Peewee ORM、DBUtils Pool、pymysql | 不解析页面、不发起网络请求 |

## 💡 关键设计模式

### 1. Client-Service 分离模式（本项目核心）

这是本项目最核心的设计决策：

```
Client（数据获取层）              Service（业务编排层）
┌─────────────────┐          ┌─────────────────────┐
│ EastmoneyClient │          │ AStockService        │
│  .fetch_kline() │ ──返回──→│  .sync_kline_daily() │
│  .fetch_lhb()   │   dict   │  ._batch_upsert()    │
│                 │          │  ._random_delay()    │
└─────────────────┘          └─────────────────────┘
```

**为什么需要这个分离？**

- Client 只负责**怎么拿数据**（url、参数、headers、cookie）
- Service 只负责**拿到数据后做什么**（清洗、转换、存库、错误处理）
- 换数据源只需换 Client，存库逻辑不变
- 换存储方式只需改 Service，请求逻辑不变

代码实例（来自项目 `business/stock/a_stock_service.py`）：
```python
class AStockService(BaseStockService):
    def __init__(self):
        self.client = EastmoneyClient()  # Client 负责拿数据
    
    def sync_kline_daily(self, symbol, period="daily", ...):
        resp = self.client.fetch_kline_daily(symbol, period, ...)  # 拿数据
```

### 3. StoragePipeline 批量写入

批量写入而非逐条写入，大幅减少数据库连接开销：

```python
class StoragePipeline:
    def __init__(self, batch_size: int = 500):
        self._buffer: list[dict] = []
    
    async def process_item(self, item: dict):
        self._buffer.append(item)
        if len(self._buffer) >= self.batch_size:
            await self.flush()  # 满 500 条统一写入
```

### 4. 断点续传管理器

爬虫中断后，不需要从零开始：

```python
class CheckpointManager:
    def get_pending_ids(self, all_ids: List[str]) -> List[str]:
        """返回尚未完成的 ID 列表"""
        completed = set(data.get("completed_ids", []))
        return [i for i in all_ids if i not in completed]
```

## ⚠️ 易错点与常见误解

1. **把 Client 和 Service 混在一起写** → 后续换数据源时要重写整个文件，正确做法是分离职责
2. **逐条 INSERT 导致性能极差** → 必须批量写入（至少 500 条一批），用 `executemany` 或 `bulk_create`
3. **忘记数据源字段与 DB 字段的映射** → API 返回中文列名（如"涨跌幅"），数据库用英文（change_pct），Service 层负责做映射
4. **没有断点续传机制** → 5000 只股票爬到第 4900 只时网络断开，没有 checkpoint 就得重来
5. **请求不做限速** → 高频请求触发反爬，必须做随机延迟（2~5s）
