## 困惑 1：Linear(hidden_size, vocab_size) 为什么要做这个映射？

### 我的困惑

"hidden_size 是 256，为什么要映射到 vocabulary_size=100？这个维度怎么定下来的？W 为什么是转置的？"

### 解答过程

**核心**：解码器每一步的任务就是**从词表里选一个词**。

```
LSTM 输出 h: 256维的抽象向量（人看不懂的内部表示）
     ↓ Linear(256, 100)
logits: 100维（每个维度 = 词表里一个词的得分）
     ↓ softmax
probs: 100维（每个维度 = 对应词的概率，加起来=1）
     ↓ argmax
pred: 1个整数（概率最大的词的 ID）
```

- `vocabulary_size` 决定输出维度：词表有 100 个词，logits 必须是 100 维
- `hidden_size` 是 LSTM 内部的"思考维度"，和词表大小无关
- 两者通过 Linear 层连接：Linear 把"抽象想法"翻译成"每个词的得分"

**W.T 的问题**：PyTorch 的 `nn.Linear(256, 100)` 把权重存成 `(100, 256)` 而不是 `(256, 100)`，所以计算时要用 `h @ W.T`。这不是数学需要，只是 PyTorch 的 API 存储习惯。

```
h:    (batch, 256)
W:    (100, 256)     ← PyTorch 存反了
W.T:  (256, 100)     ← 转置回来才能做矩阵乘法
h @ W.T → (batch, 100)
```

### 最终理解

> 256 维是 LSTM 的"想法"，100 维是"词表上每个词的得分"，Linear 就是翻译这两者的桥梁。W.T 只是 PyTorch 的存储习惯问题。

## 困惑 2：为什么 Seq2Seq 不是逐词对应翻译？

### 我的困惑

"每个 token 做一次 LSTM → Linear → Softmax 转换，得到一个结果，这不就是翻译吗？"

### 解答过程

我描述的过程其实是**同步多对多（N→N 等长标注）**——每个输入 token 立刻输出一个标签。这是词性标注、NER 这类任务的结构，不是 Seq2Seq。

**Seq2Seq 是分两个独立阶段的**：

```
阶段一（编码器）：只读不输出
  逐词读入 → 更新 h, c → 不做任何选词操作 → 最终输出 (h, c)

阶段二（解码器）：从 (h, c) 开始逐词生成
  (h, c) + <SOS> → 选词 → "Je"
  (h, c) + "Je" → 选词 → "t'aime"
  ...
```

**逐词翻译做不了 Seq2Seq 的三个根本原因**：

1. **词数不对**：英文 3 个词，法文可能 2 个词或 4 个词，无法一一对应
2. **词序不对**：英文 "a red apple"，法文 "une pomme rouge"（形容词在后），逐词翻译按英文顺序输出，语序全错
3. **没有上下文**："bank" 可以是银行也可以是河岸，逐词翻译看不到后面的词，无法判断

### 最终理解

> 编码器是"先通读全文"，解码器是"再逐词口译"——不是看一个字翻一个字。逐词翻译是标注任务（NER、词性标注），不是 Seq2Seq。

## 困惑 3：LSTM 门为什么需要两个权重（W_x 和 W_h）？

### 我的困惑

"每个门为什么有 W_x 和 W_h 两个权重？一个不行吗？"

### 解答过程

每个门要做**一个决策**，但决策需要考虑**两个信息源**：

```
W_x → 新输入的权重（衡量当前词 x_t 的影响）
W_h → 旧记忆的权重（衡量已有记忆 h_{t-1} 的影响）
```

- 只有 W_x：只知道眼前，不管过去 → 跟没记忆一样
- 只有 W_h：只知道过去，不管眼前 → 看到新词也无反应
- 两个都要：才能做出"既考虑新输入、又利用旧记忆"的决策

举例——遗忘门的决策"要不要忘掉旧记忆"：

```
看 x_t（当前词）：当前词说"但是"→ 可能要转折，旧信息该忘了
看 h_{t-1}（记忆）：旧记忆里有主语信息 → 还需要，不该忘

两个信息互相矛盾 → 必须同时看才能做出正确决策
→ 门输出 = σ(W_x · x_t + W_h · h_{t-1} + b)
```

### 最终理解

> W_x 衡量"现在看到了什么"的影响，W_h 衡量"之前记住了什么"的影响。两个权重 = 两把尺子，同时衡量两个信息源才能做出好决策。

## 困惑 4：编码器和解码器是分开训练的吗？用的是不同的语料库吗？

### 我的困惑

"编码器和解码器用不同语料库吗？还需要分开训练吗？解码器不需要训练语料吧？"

### 解答过程

**三个误解全部纠正**：

**误解 1：用不同语料库？❌**

训练数据是**双语配对**，一条样本的两半分别喂给编码器和解码器：

```
训练样本1: 英文 "I love you"     ← 编码器吃这个
           法文 "Je t'aime"       ← 解码器吃这个

同一个语料库，每条数据都是原文+译文的配对
```

**误解 2：分开训练？❌**

一个 forward → 一个 loss → 一次 backward → 编码器和解码器的参数**同时更新**：

```
1. 编码器吃原文 → 输出 (context_h, context_c)
2. 解码器吃译文（Teacher Forcing）→ 输出 logits
3. 算损失：logits vs 真实译文 → CrossEntropyLoss
4. 反向传播：梯度同时更新编码器和解码器的参数
```

**误解 3：解码器不需要语料？❌**

解码器必须有目标语言的真实文本——这就是 Teacher Forcing 的输入。没有目标文本就无法算损失，无法训练。

### 最终理解

> 一条训练数据 = 双语配对；一个 forward → 一个 loss → 同时更新两边参数；编码器和解码器是同一个模型的两部分，不是分开训练的。

## 困惑 5：解码器第一步为什么输入 `<SOS>` 而不是直接喂译文？

### 我的困惑

"已经有译文的 embedding 和编码器的 h、c 了，为什么第一步还要输入一个空的 `<SOS>`？"

### 解答过程

解码器的逻辑是**每一步的输入 = 上一步的输出**。但第 1 步没有"上一步的输出"——生成还没开始，前面是空的。

`<SOS>` 就是填这个空——它是一个特殊的"启动信号"：

```
第1步: 输入 <SOS> → "开始翻译！" → 预测 "Je"
第2步: 输入 "Je" → 预测 "t'aime"
第3步: 输入 "t'aime" → 预测 <EOS> → 结束
```

类比：翻译员脑子里已经有了对原文的理解（h, c），但需要跟她说一句"开始吧"，她才会动笔。`<SOS>` 就是这句"开始吧"。

训练时的输入输出对照：

```
解码器输入:  <SOS>  Je     t'aime
               ↓      ↓       ↓
解码器输出:  Je     t'aime  <EOS>

目标（算Loss用）: Je     t'aime  <EOS>
```

解码器输入比目标序列右移了一位，前面补 `<SOS>`。

### 最终理解

> `<SOS>` 是启动信号，填"第 1 步没有上一步输出"的空。它不是空的，是一个特殊的 token，告诉解码器"开始生成"。

## 困惑 6：为什么要把上一步的输出当做下一步的输入？不是已经有译文了吗？

### 我的困惑

"已经有译文的 embedding + 编码器的 h、c 了，为什么还要把上一步输出当输入？那不就变成 4 个向量了？"

### 解答过程

**"上一步的输出"和"译文的 embedding"是同一件事，不是两件事！**

训练时（Teacher Forcing）：

```
decoder_input = [<SOS>, Je, t'aime]   ← 译文的 embedding 序列

第0步: 输入 = decoder_input[0] = <SOS> 的 embedding   ← 这就是"上一步的输出"
第1步: 输入 = decoder_input[1] = "Je" 的 embedding     ← 这就是"上一步的输出"
第2步: 输入 = decoder_input[2] = "t'aime" 的 embedding  ← 这就是"上一步的输出"
```

所以不是 4 个向量，而是：

```
输入: x_t（词 embedding）        ← 1 个
状态: h, c（LSTM 内部维护）      ← 不是额外喂的，LSTM 自己带着走
```

**为什么不能每步直接喂译文的对应词？** 因为推理时没有译文！

```
训练时: 有译文 → Teacher Forcing 用真实词
推理时: 没有译文 → 只能用自己的预测词作为下一步输入

训练时必须模拟推理的方式 → 训练和推理行为一致 → 避免 Exposure Bias
```

### 最终理解

> 训练时"上一步输出"和"译文 embedding"是同一回事。推理时没有译文，只能用自己的预测。必须让训练和推理的输入方式一致。

## 困惑 7：推理时只用解码器吗？编码器还需要吗？

### 我的困惑

"训练时编码+解码，推理时只拿解码器来推理？"

### 纠正

**推理时编码器也要用！** 没有编码器，解码器根本不知道原文在说什么。

```
推理的完整流程：
1. 用户输入原文 → 编码器处理 → 输出 (context_h, context_c)  ← 必须有编码器！
2. 解码器基于 context 开始自回归生成

训练和推理的区别：
  编码器: 始终要跑
  解码器: 始终要跑
  区别: 解码器的输入来源不同
    训练: 喂译文（Teacher Forcing）
    推理: 喂 <SOS>，然后自回归
```

### 最终理解

> 编码器永远要跑。训练和推理的唯一区别是解码器的输入来源：训练喂译文，推理喂自己的预测。

## 困惑 8：src_len 和 trg_len 是谁定的？怎么定的？

### 我的困惑

"编码器输入包含几个 token 是谁定的？怎么定的？正常怎么计算？"

### 解答过程

**真实项目中，token 数量是数据决定的。**

每个样本的句子长度天然不一样。一个 batch 里长度不同，无法组成 tensor → **Padding（填充）**：找 batch 里最长的那个，短的补 `<PAD>` 到一样长。

```
样本1: [I, love, you]                    → 3个向量
样本2: [The, weather, is, nice, today]   → 5个向量

Padding:
样本1: [I, love, you, <PAD>, <PAD>]     → 补到5
样本2: [The, weather, is, nice, today]  → 本来就是5
```

所以：

```
src_len = 当前 batch 中源序列的最长长度（不够的补 PAD）
trg_len = 当前 batch 中目标序列的最长长度（不够的补 PAD）
```

每个 batch 的 src_len 和 trg_len 可能不同。手推练习里用固定值是跳过了数据预处理，用 `torch.randn` 直接模拟 Embedding 后的结果。

### 最终理解

> src_len 和 trg_len 由数据决定——每个 batch 取最长句子的长度，短的补 PAD。练习中用固定值是简化模拟。
